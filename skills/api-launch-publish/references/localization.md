# Localization Rules

## Principle

Localization means rebuilding the argument for a reader in that language. It is not translating sentences after the English draft is finished.

Before writing a locale, choose:

1. The local search question.
2. The reader's working context.
3. Local examples or terminology that make the argument clearer.
4. A platform-native call to action.

## English

- Prefer compact, direct prose and strong verbs.
- State the technical conclusion early; then show the trade-off.
- Use global developer vocabulary consistently: agent runtime, sandbox, tool call, session, artifact, audit trail.
- Do not force Chinese market context into an English article unless it materially changes the analysis.

## Simplified Chinese

- Write from scratch after understanding the source argument; never retain English sentence order.
- Begin with a conclusion or a familiar engineering pain point.
- Use Chinese technical-community language naturally: 跑不起来、踩坑、兜底、接不住、拼装、上线后翻车. Do not overuse slang.
- Keep product names and technical terms in English when that is how builders use them: API、SDK、runtime、sandbox、MCP、token.
- Add spaces around English words and numbers, use Chinese punctuation, and split long modifier chains into shorter sentences.
- A Zhihu version should answer the question directly. It can be more explanatory and less brand-forward than the blog version.

## Additional Locales

Do not add a new locale by translating the Chinese or English file. Add a section here first defining the reader, search intent, conventions, and restricted claims for that locale.

## Review Questions

- Would a fluent reader believe this was drafted in their language first?
- Does the title match how they would search or ask the question?
- Did examples, metaphors, and CTA change when the audience changed?
- Is a literal translation hiding the author's actual judgment?
