# 内容深度与真实性规则

> 本文件定义博客文章的深度要求和真实性标准。所有文章必须遵守。
> 创建日期：2026-07-31

---

## 1. 深度要求（不允许水文）

每篇文章必须通过「深度检查」，否则打回重写：

### 必须包含的深度元素

| 元素 | 说明 | 示例 |
|---|---|---|
| **真实场景** | 至少 2-3 个具体使用场景，写清谁在用、做什么、需要什么数据 | 竞品监控 agent 每天查 10 个账号 30 次调用 |
| **具体数字** | 调用次数、响应时间、费用、对比数据——不是"快"而是"1-5 秒" | $0.001/次 × 30 次/天 = $0.03/天 |
| **对比矩阵** | 多种方案在相同场景下的表现对比，不是功能列表 | 同一个视频详情请求：同步 API 1-5s vs Apify 15-45s |
| **代码/JSON 示例** | 真实 API 响应结构或调用代码，展示实际数据格式 | Douyin video detail 返回的完整 JSON 结构 |
| **成本计算** | 按场景给出月/日费用估算，用乘法而非形容词 | 10 账号 × 3 端点 × $0.001 = $0.90/月 |
| **架构影响** | 技术选择如何影响 agent 整体设计 | 同步 vs 异步路径对 agent turn 时间的影响 |
| **局限与边界** | 每个推荐方案的真实限制 | "只覆盖 4 个平台，Instagram/YouTube 得另找" |

### 禁止的浅度模式

- ❌ 纯功能罗列（"支持 A、B、C、D"）无场景说明
- ❌ 形容词代替数字（"非常快""价格合理""覆盖广泛"）
- ❌ 所有方案写得一样深（主推方案要深 3 倍）
- ❌ FAQ 回答只有一两句话（每个 FAQ 要有数字或代码支撑）
- ❌ 没有 trade-off 的推荐（任何推荐必须说"但是..."）
- ❌ 结尾只是重复开头的摘要

### 深度自检清单

写完后逐项检查：

- [ ] 读者看完能算出自己场景的月费用吗？
- [ ] 读者能判断哪个方案适合自己的 agent 架构吗？
- [ ] 文章有没有至少一个"只有真正用过的人才知道"的洞察？
- [ ] 对比是否在相同维度（同一个任务在不同方案下的表现），而非各说各的？
- [ ] 每个方案的局限是否具体到了场景级别（"场景 3 不行"而非"有些限制"）？

## 2. 真实性标准

### 数字必须有来源

| 数据类型 | 允许来源 | 不允许 |
|---|---|---|
| 平台接口数量 | 生产 `/v1/models` API 响应 | 编造或从旧文档推测 |
| 价格 | 生产 API 的 `base_price` 字段、官方定价页 | 记忆中的数字、"大约" |
| 响应时间 | 实测（记录测试条件）或官方 SLA | 编造"通常 1-3 秒" |
| 竞品数据 | 竞品官网、官方文档、公开 API | 编造竞品特性 |
| 用户数/客户数 | `source_facts` 中有 source_url 的条目 | 任何无来源的客户声明 |

### 可以估算但必须标注

以下情况允许估算，但必须说明估算方法：

- "按 $0.001/次计算"（标注了单价来源）
- "响应时间 1-5 秒（基于 10 次测试的范围）"
- "Apify 费用约 $0.005-0.02/条（基于官方定价页的 compute unit 估算）"

### 绝不允许

- ❌ 编造 benchmark 数字
- ❌ 编造响应时间（没测过就不写具体数字）
- ❌ 编造竞品不具备的特性
- ❌ 把 registry 数据（仓库签入的测试数据）等同于生产数据
- ❌ 把一次测试结果写成"always"

## 3. 场景驱动的文章结构模板

对于评测/对比类文章（best-of、model-comparison、developer-tools），推荐结构：

```markdown
# 标题

> TL;DR（含关键数字）

## 为什么这个选择重要（1 段，不要泛泛而谈市场趋势）

## N 个真实场景（暴露各方案差异的场景设计）

### 场景 1：xxx
- 需要什么
- 调用量/频率
- 关键要求

### 场景 2：xxx
...

## 方案在场景下的对比矩阵（表格）

## 方案 1：深度评测
- 实际返回结构（JSON 示例）
- 费用计算表
- 真实局限

## 方案 2：深度评测
...

## 架构影响（选择如何改变 agent 设计）

## 平台层的价值（SandBase 定位，不排名）

## FAQ（每个答案有数字支撑）

## 要点（可执行的结论）
```

## 4. SandBase 的写法（重申）

- SandBase 不参与横向排名表
- SandBase 出现在"让这些 API 对 agent 更易用"的段落
- 强调开放生态 + runtime 编排，不强调"我们有更多 API"
- 必须写 SandBase 的具体贡献：契约归一、skill 组合、可观测性
- 可以写接入邀请 CTA，但不是每篇都加
- 不暴露上游供应商名称（不提 TikHub）
